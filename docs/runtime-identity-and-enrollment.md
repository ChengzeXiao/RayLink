# Runtime identity, metering authorization and enrollment recovery

Account email is editable; Runtime identity is persistent. New Users receive an internal `rl-user-<User ID>` name. `clientCredential().runtimeName` and `runtimeSnapshot().users[].runtimeName` supply the same identity to inbound authentication, client authentication and the V2Ray stats whitelist. Existing installations retain their captured username during migration, avoiding an unnecessary client credential change.

Legacy names remain permanent aliases of their original User ID. Renaming or reusing an email cannot transfer its counters. Deleted Users leave an alias tombstone. Aliases belonging to the same User and Runtime instance share one checkpoint and monthly watermark, preventing double billing. Historic applied configurations are matched by protocol UUID/password when recovering old email aliases. If retained evidence associates one legacy name with conflicting Users, that alias is quarantined instead of guessing its owner; affected Users receive an unambiguous ID-based Runtime name on the next compilation. Existing incorrect historic bills cannot be reconstructed automatically from an ambiguous counter name.

A remote Host can report billable usage only for Users found in a successfully completed `publish-config` task. Migration rebuilds this index from retained successful tasks; merely queued configurations do not grant metering authority. Grant intervals are retained after scope removal so a delayed sample can still be attributed to a legitimately installed old configuration. Sample observation time must lie within a grant interval, with the existing five-minute clock-skew tolerance; the existing seven-day sample receipt limit still applies. A Host whose successful task history has already been deleted needs a fresh successful configuration publication before billing resumes. Local collector reports remain a trusted control-plane boundary.

New RayLink Nodes persist their X25519 keypair before sending enrollment. The control plane consumes the enrollment token and commits a credential envelope encrypted to that key in the same SQLite transaction. A retry with the original token and public key receives only the encrypted envelope, which requires the Node's private key to open. A different key cannot replace an enrolled Host or obtain a usable credential. Concurrent enrollment operations on one Node share a promise; independent control-plane connections serialize token consumption in `BEGIN IMMEDIATE`.

Older Nodes retain their one-time plaintext enrollment response for compatibility. Automatic lost-response recovery requires the updated Node and its persisted keypair. An enrollment already lost before this migration has no recoverable receipt and cannot be repaired by inventing or reopening its consumed token. Existing enrolled Nodes keep their current secrets and do not re-enroll during upgrade.

Regression coverage: `tests/node-enrollment-recovery.test.js`, `tests/usage-identity.test.js`, the existing monthly/checkpoint tests, and the native protocol and metering fixtures. Native metering assertions must use `runtimeName`, not the editable email.
