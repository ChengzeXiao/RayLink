# RayLink 整体网络体检 — 2026-10-02

本报告记录对 VPS-A 与 RayLink v0.2.35 的在线体检、真实客户端传输和隔离模拟结果。检查时段约北京时间 12:04–12:20。结论是：七种协议目前具备实际传输能力，但发现出口 DNS 地址选择导致测速显著变慢、健康检查状态可能互相覆盖，以及受管证书续期未同步的隐患。手机截图中的四项持续 timeout 尚未在相同手机环境复现。同一代理被多个分组引用，截图中的重复红点不代表额外的故障服务器。

本轮产物为体检证据及修复方案，以下优化尚未作为新版本上线。测试使用内部探测身份，不修改用户额度、密码、协议端口或订阅标识。

### 1. 出口 DNS 确实增加了 gstatic 的耗时

VPS `/etc/resolv.conf` 当前使用 `8.8.8.8`、`8.8.4.4`。系统解析 `www.gstatic.com` 得到 `203.208.49.130`；对照查询 `1.1.1.1` 得到 `142.251.219.3`，阿里 DNS 得到 `142.251.218.67`。

在 VPS 上交替执行四轮 `curl --resolve`，始终访问同一个 `https://www.gstatic.com/generate_204`，保留 SNI、正常证书验证和 HTTPS，仅改变拨号 IP：

| 地址来源 | TCP 建连范围 | HTTPS 总耗时中位数 | HTTP 204 |
|---|---:|---:|---:|
| 当前系统 DNS 的地址 | 169–3266 ms | 1969 ms | 4/4 |
| Cloudflare DNS 的地址 | 1.7–3.3 ms | 92 ms | 4/4 |
| 阿里 DNS 的地址 | 1.2–1.7 ms | 75 ms | 4/4 |

这是当前测速慢的一个已确认贡献因素；不能据此宣称所有业务会快同样倍数，也不能直接定性为 DNS 污染。可将运行时出口 DNS 改为经过验证、带备用的解析方案，并保持缓存与回滚。不要把本次临时 CDN IP 硬编码进长期配置。

另一测速地址 `https://cp.cloudflare.com/generate_204` 在 VPS 三轮耗时约 92–103 ms。更换测速目标可以减少该目标的干扰，但数字变小本身不等于实际业务或物理线路变快。

### 2. 健康检查能够误判、互相覆盖

当前 Mihomo 导出使用同一测速 URL，TCP 组预算 5 秒，智能/回退组 8 秒，UDP 组 12 秒，且 `unified-delay: true`。真实 Mihomo 1.19.25 的统一延迟测试包含两次 HEAD，完整预算包括握手与请求，显示值通常只是后一次的延迟。[Mihomo 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.25/adapter/adapter.go#L164)

两个实际核心模拟：

- 每次 HEAD 响应 3.5 秒：5 秒整体预算 timeout，8/12 秒通过；同一 Trojan 随后的 128 KiB 业务传输正常。
- 首响应 6 秒：5.4 秒时四个 TCP 代理被判失败，fallback 切至 Hysteria；8.25 秒其他组探测成功，同批 TCP 又恢复并切回 VMess。

`max-failed-times: 3` 是业务拨号失败触发额外检查的阈值，不能视为“连续三次测速失败才判死”。[实现依据](https://github.com/MetaCubeX/mihomo/blob/v1.19.25/adapter/outboundgroup/groupbase.go#L260)

实际应用构建的七协议订阅，未手动点测速时，启动模拟观察到 44 次 HEAD、峰值并发 22；当智能组包含全部协议时为 50 次、并发 25。仅将 `lazy` 改为 true 无法消除首次探测；实验性单组检查降至 14 次、并发 7，但该单组配置不具备现有全部选择语义，不能直接作为上线方案。

建议将健康采样与策略选择分开：一次节点采样供各组使用，预算一致；再依据中位延迟、失败率及切换容差选路。需验证所支持的客户端版本，避免为减少探测而破坏兼容性。放宽 timeout 只能减少误判，不能降低网络延迟。

### 3. 证书自动续期遗漏：目前有效，10 月 26 日存在到期风险

| 证书位置 | 签发日期 UTC | 到期日期 UTC |
|---|---|---|
| Caddy 受管 `node.cyclelink.org` 证书 | 2026-09-26 | 2026-12-25 |
| sing-box Runtime 的同域名证书副本 | 2026-07-28 | 2026-10-26 |

两者 SHA-256 指纹不同。七个代理协议使用同一个旧副本。当前证书验证成功，所以它不是本次高延迟或 timeout 的已证实原因；若到期前仍不更新副本，共享该副本的 TLS 新连接会受影响。

代码路径是协议启用时 `prepareLocalCertificate()` 调用 `LocalTlsAssetStager.stage()`；普通发布、主控启动和定时 reconcile 不重新从 Caddy 复制。后台也没有对应同步任务。文件型 certificate 配置不会自行完成 ACME 签发。

最小修复方案：为 RayLink 管理的 Caddy 副本建立启动及定时同步任务；按域名去重，校验域名/有效期/密钥配对，内容变化才更新，保留权限与回滚；更新后验证各 TCP/QUIC 入口实际握手的证书指纹，并通过 MCP/UI 展示有效期和同步错误。不要通过重复“启用协议”实现续期，它还会修改端口与发布状态。

代码入口：`server/protocol-activation.js:420`、`server/tls-assets.js:80`、`server/app.js:2394`。

### 4. 智能分流与真实故障恢复的边界

国内直连、海外代理、AI 独立出口的总体分组存在。默认普通代理列表第一项是“故障回退”，该组选择第一个活节点，不保证最低延迟。模拟 VMess 182 ms、其余 20–22 ms 时，自动优选组已选择较快节点，默认 fallback 仍保留 VMess。

用户截图已经选择“RayLink 智能”，因此上述默认项不能直接解释本次截图。建议保留 AI 出口粘性，普通流量使用带切换容差的自动优选，并保证 TCP 全失败时仍能回退至客户端已验证的 UDP 通路。

现在七个协议都位于同一台 VPS；多协议回退能缓解协议路径故障，无法解决该主机或同一公网线路整体不可用。若目标是显著低于当前约 180 ms 的连接时延，需要实测更合适的线路/地域；拥塞控制参数无法消除既有传播时延。

## 七协议真实公网验证

测试使用 Mihomo 1.19.25 加载实际线上生成的完整订阅，保留 DNS、域名/IP 映射、分组和规则；测试替换为内部探测凭据、隔离本地监听，并绑定本机 Wi-Fi 网卡 `en0`。42 次原生测速显式使用 12 秒预算；后 14 次 GET/下载切到 global 模式并逐个强制选择代理。服务端为现网 sing-box 1.14.2。TLS 证书验证保持开启。

特别校正：本机默认路由经过 `utun4`。最初的普通 ping/TCP connect 返回不到 1 ms，属于本地隧道路由干扰，已排除，未作为公网 RTT 证据。绑定 `en0` 后的四个 TCP 端口各四次连接全部成功，中位数为 181–191 ms。该数据不代表用户手机的网络。

两种测速地址 × 七协议 × 三轮，共 **42/42 成功**；随后七项实际 HTTPS GET 204 及七项 1 MiB 文件下载均通过，共 **56/56 检查通过**。这些结果证明逐协议可用性，不代表默认 5/8 秒组健康检查或智能分流选择本身已通过实网验收。

## 补充隔离验证

本地 sing-box 1.13.14 ↔ Mihomo 1.19.25，随机测试凭据和独立 CA，保持严格证书验证：七协议均完整传输 128 KiB；完整导出分组七项并发测速通过。仅把客户端 SNI 改错，Trojan/VLESS/AnyTLS/Hysteria2 均返回证书名称不匹配，证明校验未被绕过。客户端 DoH 图曾成功返回真实 A 记录，也出现过一次独立超时；不能将该次本地网络波动归因于生产 VPS。

这些结果排除了现代 Mihomo 对当前导出的普遍不兼容；仍不能替代用户准确 iOS 客户端版本、缓存订阅、Wi-Fi/移动网络的复测。

## 修复验收建议

1. 出口 DNS：同一测速 URL 做修改前后交替测试，保留证书验证；再检验 Google、Cloudflare 和实际业务域名的解析/首包/下载，故障时能回退，不持久硬编码 CDN IP。
2. TLS：模拟续期，验证新证书进入各协议握手；坏证书、错误域名、密钥不匹配、并发发布和远端离线应可回滚/重试；提前展示到期告警。
3. 健康检查：以当前 44–50 次启动 HEAD 为基线降低重复量；慢但可传输的节点不在多组之间反复红绿；确实失效的节点仍在规定预算内切换。
4. 用户侧：完整订阅更新后，分别验收 Wi-Fi 与移动网；记录协议成功率、冷连接、DNS、首包和持续下载；手机截图四个 timeout 未实机通过前，不宣称已修复。
