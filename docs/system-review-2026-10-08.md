# RayLink 全系统深度审查与优化建议

审查日期：2026-10-08。代码基线：`313999996202296eb40d853d8d6368717262af2d`，版本 `0.2.46`，分支 `codex/ai-protocol-resilience`。

后续修复与验收记录见 [系统修复报告](system-fixes-2026-10-08.md)；下文保留审查时的基线结论。

本轮覆盖控制台、REST/MCP 权限、用户与会话、流量计量、自然月重置、Node 注册与任务、配置发布与回滚、订阅转换、DNS/智能分流、AI 上游、运行监控、备份和部署验收。采用代码审查、隔离故障复现、原生内核请求及线上只读检查。未修复源代码、发布版本、修改线上配置或重启生产服务。

## 1. 结论

当前单服务器、7 用户规模下，服务与数据库运行正常，已有权益撤销、计量水位、任务顺序、自然月事务和原生内核测试等基础保护。但正常流程测试不能覆盖所有故障路径：本轮确认 **11 项不同缺陷，其中 3 项 P1、8 项 P2**。它们需要特定角色、操作、并发或故障条件；没有证据表明线上已经发生权限利用、流量错计或配置漂移。

优先顺序应为：**权限与撤销安全 → 可靠注册和计量归属 → DNS/订阅兼容与发布状态 → 减少中断、客户端诊断和灾难恢复**。继续堆叠域名规则或修改 BBR，无法解决这些跨层问题。

这里的 P1 表示应优先修复的权限或核心操作可靠性问题，P2 表示在限定场景中产生错误结果、连接失败或误导操作的问题；不是外部安全评分。

## 3. 已确认缺陷

### R01 · P1 · Auditor 可通过 REST 获取订阅凭据及协议私密字段

**位置**：`server/app.js:103`、`:1449`、`:1837`，`server/database.js:1808`。

普通 GET/HEAD 被统一映射为 `read` 权限，而部分 GET 返回的是敏感配置。隔离 HTTP 复现中，Auditor 的写操作被正确拒绝（403），但用户订阅接口返回 200 并包含订阅 bearer；bootstrap 返回的协议中包含 Reality 私钥。取得的订阅 bearer 还能下载包含 Runtime 用户凭据的完整订阅。

这要求已有 Auditor 登录权限，不是匿名直接读取；目前线上只有 Owner。MCP 对同类敏感操作已有更严格限制，REST 与 MCP 边界不一致。

**建议**：按资源和操作授权，不能按 GET 判断是否安全。默认使用脱敏 DTO；凭据读取使用独立权限并记审计事件。把 REST 与 MCP 的授权、字段投影放到共享业务层。验收必须覆盖每个角色的负向读取测试和已泄露订阅的真实下载能力。

### R02 · P1 · 回滚历史部署可恢复已禁用用户的 Runtime 凭据

**位置**：`server/singbox/runtime-manager.js:232`、`:247`。

回滚直接发布历史配置中的用户与凭据。隔离复现：发布用户 → 禁用并完成权益对账 → 回滚最早部署，数据库用户仍为 disabled，但发布给适配器的 Runtime 配置再次包含该用户。正常后台对账可能随后修正；默认约 60 秒窗口不能保证远端失败时立即恢复安全状态。

**建议**：回滚协议、拓扑和非授权配置时，用户凭据必须根据**当前有效权益**重新编译；拒绝任何扩大现有授权的回滚。远端也应用同一约束。现有“历史快照原样重放”测试契约需要调整，而不是只添加成功回滚测试。实际停用、过期、配额耗尽和区域授权撤销都应加入回滚验收。

### R03 · P1 · Node 首次注册成功响应丢失后，自动重试无法恢复

**位置**：`server/database.js:2195`，`web/node/raylink-node.mjs:1412`。

控制面先消费注册 token 并保存节点 secret 哈希；Node 收到成功响应后才保存密钥和认证状态。隔离复现中，数据库提交后人为丢弃响应，控制面显示已注册，Node 却没有认证凭据；重试被拒为 token 已消费，轮换注册 token 又返回 `NODE_ALREADY_ENROLLED`。

**建议**：请求前持久化节点密钥对和注册请求 ID；同一密钥持有者可幂等恢复注册结果，或提供明确、安全的重新注册流程。不能简单放开已消费 token，让其他密钥接管节点。验收涵盖提交后断网、响应丢失、落盘失败和进程重启。

### R04 · P2 · 可修改的邮箱承担计量身份，迟到样本可能漏计或计入别人

**位置**：`server/database.js:1888`、`:1898`、`:2805`。

计量以当前邮箱查用户，checkpoint 也保留邮箱。复现：A 累计 1,000 字节后改邮箱，旧邮箱累计 1,300 的迟到样本被忽略；B 使用 A 的旧邮箱后，旧累计 1,500 的样本把 500 字节计给 B。

**建议**：Runtime 计量名改为基于不可变 user ID 的标识；邮箱只负责登录和展示。迁移保留旧标识的历史归属，避免旧别名立即复用。继续按 Host、Runtime 实例、自然月水位去重；不能把此修复退化为重新按累计总数扣费。

### R05 · P2 · Node 可上报从未获授权用户的流量，消耗其他用户额度

**位置**：`server/database.js:1887`，`server/app.js:2424`。

隔离 HTTP 复现：已认证的 US Node 上报仅授权 SG、且从未下发到该 Host 的用户，接口仍返回 200 并计入 1 MiB。错误或被控制的 Node 因而能影响别人的配额。当前线上只有本机 Host，未观察到远端利用。

**建议**：将样本绑定到 Host、实际应用的配置代数与不可变用户 ID，验证该代数的历史授权成员；未知身份隔离待查。不能只检查用户“现在”的区域权限，否则撤销前的合法迟到样本也会被误拒绝。

### R06 · P2 · 用户重置密码与正在进行的旧密码登录存在竞态

**位置**：`server/database.js:1578`、`:2894`，`server/app.js:2293`。

密码校验异步完成后未重新检查用户版本。HTTP 复现：旧密码登录开始 → 管理员重置密码、撤销会话 → 旧校验结束并创建新会话；登录返回 200，之后 `/me` 仍 200，而重新发起旧密码登录已失败。管理员认证已有类似的校验后重读保护。

**建议**：会话创建前验证当前 password/auth version、邮箱和门户状态；把重置与会话版本失效作为同一不变量。用确定性并发 HTTP 测试验证重置后不再产生有效旧凭据会话。

### R07 · P2 · 登录限流在失败后记数，并发请求可穿过门槛

**位置**：`server/app.js:1225`、`:1240`、`:2265`。

同一来源同时提交 32 次错误登录，全部进入密码校验并返回 401；下一次串行请求才返回 429。当前逻辑限制已完成失败数，无法限制同批在途请求。

**建议**：昂贵密码校验前原子预留预算，同时限制每 IP、账户及全局在途校验数，并正确释放预算。避免只降低单次次数而仍保留并发窗口。本轮没有对线上发起爆破或负载攻击。

### R08 · P2 · 发布已提交，但刷新失败时界面显示“发布失败”并鼓励重试

**位置**：`web/app.js:3645`、`:3676`。

真实发布函数在 DOM/API 隔离环境中复现：发布 POST 成功，随后 `loadBootstrap()` 失败，界面仍提示“发布失败”并展示“重试发布”。回滚存在相同处理结构。重试可能再次重启 Runtime，放大网络中断。

**建议**：把“操作提交结果”和“页面刷新结果”分开。保留 deployment ID，显示“发布已提交，状态刷新失败”，允许查询该任务；不要自动重放变更。用户保存流程已有类似处理，可统一为操作结果组件。此项是 JS 边界复现，未声称完成浏览器交互验收。

### R09 · P2 · 状态只比较数据库快照，活动配置漂移仍可显示已应用

**位置**：`server/app.js:665`、`:689`，`server/singbox/local-adapter.js:196`。

隔离复现使用真实 Store、编译器及本地适配器，模拟 systemd 在线：成功发布后改变活动文件中的上游地址，设置接口仍返回 `runtimeSync.status=current`。该状态只比较期望编译 checksum 与数据库 active deployment，未读回活动文件；同样的判定还可能跳过重发。

**建议**：分别保存 desired、published、read-back 和 running generation。读取实际配置 checksum，并绑定已确认的启动/应用证据及 Runtime 实例 ID。单纯文件哈希也不能证明进程已加载该文件。配置一致与上游可访问必须是两个状态。**本轮线上检查未发现此类漂移。**

### R10 · P2 · HTTPUpgrade 导出的 Mihomo 传输格式可校验却不可实际连接

**位置**：`server/subscriptions/formats.js:344`、`:358`，支持声明 `docs/sing-box-protocol-support.md:18`。

当前转换器输出 `network: httpupgrade`、`http-upgrade-opts`。产品编译器 + 真实 sing-box 1.13.14 服务端 + Mihomo 1.19.25 客户端的本地请求对照中，普通 VLESS 和 WebSocket 成功返回目标正文，HTTPUpgrade 返回空响应（curl 52），两端语法检查却都通过。

Mihomo 官方格式把 HTTPUpgrade 放在 `network: ws` 的 `ws-opts.v2ray-http-upgrade` 中，见 [官方传输配置](https://wiki.metacubex.one/en/config/proxies/transport/)。因此不能依赖 `mihomo -t` 证明该节点可用。

**建议**：按目标内核正确映射；无法支持的组合明确过滤或拒绝。加入逐传输真实请求验收。VMess/Trojan 共享转换器，但本轮仅请求验证了 VLESS；此项尚未以生产服务端 1.14.2 重跑，不能声称当前线上 timeout 就由它造成。

### R11 · P2 · 住宅出口的普通域名捷径绕过 Runtime DNS 回退

**位置**：`server/routing/ai-upstream-domains.js:46`，`server/singbox/config.js:49`，`server/singbox/runtime-dns.js:63`。

启用住宅上游时，已到达 Runtime、命中自定义 `proxy` / `direct` 动作的域名会进入提前终止的 `route → direct`，排在显式 `resolve` 前；直连拨号只使用主 DNS，不经过包含备用 DNS 的规则链。本轮明确复现的是 `proxy` 动作；完整客户端中的 `direct` 通常不会到达 VPS，`block` 则执行拒绝。

本轮先在 1.13.14 复现，随后使用生产同版本 **1.14.2** 在 VPS 的独立回环进程验证，未使用生产配置或改变服务：主 DNS 返回 SERVFAIL、备用正常时，命中该普通域名规则的请求失败且备用未被查询；未命中规则的普通请求能回退。1.14.2 基线黑洞回退约 2,041 ms，缓存约 35 ms，私有域名隔离等基线检查通过。

**建议**：普通流量终止路由前保留显式 DNS 解析及回退；AI 流量保留原始域名交给上游；拒绝规则不应为了分流额外做 DNS 查询。添加“住宅启用 + 普通自定义域名 + 主 DNS 失败”的组合验收。未单独复现私有后缀和共享域名变体，不扩大已确认影响范围。

## 4. 网络与智能分流的优化方案

### 4.1 先稳定链路，再扩展规则

配置发布存在会中断长连接的整进程重启路径：`server/singbox/local-adapter.js:157` 在替换配置后执行整个 Runtime 的 systemd restart。隔离适配器对同 checksum 连续发布两次，记录到两次重启。用户配置变化可能走此路径，影响同进程的 SSE、WebSocket 和长 API 请求；这不是已经证明的某次 ChatGPT 重连根因。

建议依次实施：

1. **相同配置不重复重启**，但必须先确认实际文件/应用代数一致，不能沿用 R09 的数据库判定。
2. 合并短时间内相容的普通配置变更，显示待应用范围；禁用、配额耗尽和凭据撤销走即时高优先级，不等待批量窗口。
3. 发布前检查协议能力、证书、目标端口与配置；发布后验证实际入口请求、计量和撤销语义。
4. 将控制面更新与数据面重启分离。只有验证内核、协议支持后才采用动态用户更新或优雅切换，不承诺所有 sing-box 协议都可无损热更新。

### 4.2 保持清晰的分流边界

沿用最小且可解释的规则层级：局域网/私有地址安全处理 → 用户显式规则 → 明确 AI 域名 → 明确国内/国外域名与规则集 → 国内 IP 判定 → 可手动切换的未知流量兜底。具体实现必须保留已有自定义规则的优先语义，不能为了扩大国内直连而提前覆盖 AI、显式海外规则。

- 国内 App 不能仅靠 App 名维护清单。API、图片、对象存储和第三方 CDN 应综合域名分类与解析到的 CN IP 判断，避免把未知公网目标全部直连。
- 当前 v0.2.46 的国内 DNS 优选主要针对完整 Mihomo/Clash 智能订阅；不能把其他格式、全局模式或仅节点订阅视为具有相同语义。
- 当前国内 DoH 候选属于同一供应商，已有 CN-IP 响应过滤，但供应商整体故障不是独立冗余；双超时约 5 秒是已有边界。先做跨供应商、污染响应、缓存与延迟实测，再决定替换，不盲目竞速接受最快结果。
- CDN、Google 登录等共享基础设施不能整体归入 AI。AI 独立域名走指定 AI 出口，普通 Google、YouTube、X 等继续走普通策略。
- AI 固定地区/节点应由用户明确选择；不因为测速更快自动跨地区或从住宅代理切回 VPS。单台 VPS 的多协议回退无法解决该 VPS 公网 IP 完全不可达。
- 维持失败时的明确行为：住宅出口不可用时显示 AI 连接失败，普通网络保持原路径；不要隐式改变账号出口。

### 4.3 上游接入验证应分层显示

新增或增强启用前验证：**TCP 可达 → 代理协议 → 代理认证 → 目标 TLS → 目标 HTTP → 实际出口 IP**，分别记录错误和证据时间。HTTP 端口填成 SOCKS5 这类问题应在启用前发现。

现有管理端供应商探测之外，应增加通过生产入口的受控探测，验证订阅、入口协议、Runtime 规则和上游整条路径。API 返回 401 可表示目标已到达，不能展示为模型调用成功；403、验证页、429、DNS/TLS/超时分别分类。只探测预设目标、限频限量、脱敏输出，避免变成任意 URL 代理或保存浏览历史。

## 5. 数据、运维与架构建议

### 数据与计量

自然月重置已有事务、持久化周期、历史归档和跨月样本隔离，本轮未确认新的月重置缺陷。优先修复身份归属 R04/R05，再交付现有设计中的流量对账：按用户、Host、Runtime 实例、自然月显示计入/拒绝/仅基线的原因，保留可审计人工调整记录。

线上约 8.7 万 usage samples、26.6 万账本记录。应按实际查询计划验证索引、分页和保留期限，防止 bootstrap/用户列表承担全量历史查询；未凭该数量断言当前已经慢查询。约 1 GiB 主机可继续服务当前规模，但扩容应依据事件循环延迟、RSS、数据库锁等待与 P95，而不是单次 CPU 快照。

### 可靠发布与恢复

每个 Host 独立记录期望代数、应用代数和撤销确认时间；持久化发布意图和重试结果，进程退出后先对账再执行。关键撤销不能被旧发布、回滚、恢复覆盖；离线节点应持续显示未确认。

备份目前已通过文件校验和数据库完整性检查，下一步是干净主机恢复演练：数据库、订阅加密密钥、证书和必要环境配置作为同一恢复集合，恢复后验证登录、订阅解密、真实代理请求、计量、月周期和撤销。异地加密备份与实际恢复时间应另行验收；本轮未检查外部备份系统，不能断言其不存在。

升级门槛从“服务 active / API 有响应”提升为关键业务后置条件；失败时确认旧版本业务真正恢复。不要每次升级都跑全部手机矩阵，但涉及路由、DNS、TUN、协议或计量时必须选取对应真实场景。

### REST、MCP 与前端的共同业务层

`server/app.js` 约 2,700 行、`server/database.js` 约 3,200 行、`web/app.js` 约 4,600 行。文件长度本身不是缺陷，但授权/投影与操作结果不一致已经造成 R01/R08。

优先抽出能保护不变量的模块：授权与安全 DTO、用户/计量身份、注册状态机、发布/回滚状态机、诊断证据。REST、MCP 和 UI 共享这些边界及错误码，避免为三个入口分别实现授权。保留现有 SQLite 和单进程架构，当前规模无需为了拆分而引入微服务。

## 6. 实用功能建议与交付顺序

已有“运行体检”，不建议再做一个重复仪表盘。应在现有能力上补齐三个可独立验收的功能：

| 功能 | 用户能获得什么 | 最小交付与边界 |
| --- | --- | --- |
| 路由解释与客户端诊断 | 知道某个图片/API 为何慢，实际走哪个规则、组和出口 | UI/MCP 展示服务器推演与客户端实测两个来源；导入脱敏连接记录；不能把服务器推演标为手机实测 |

## 7. 修复后的 QA 门槛

1. **授权与撤销**：Owner/Operator/Auditor 每个读写操作逐项验证；禁止敏感 GET 泄露。禁用、到期、配额耗尽后，发布/回滚/恢复/迟到任务均不得恢复授权。检查实际 Runtime 新连接拒绝，不只检查数据库状态。
2. **并发与故障**：并行错误登录在昂贵校验前受限；密码重置期间旧请求不能新建有效会话；注册响应丢失和进程重启可安全续接；操作提交后刷新失败不重新变更。
3. **计量与自然月**：不可变用户身份、邮箱复用、跨 Host、乱序/重复、实例切换和撤销后迟到样本；北京时间月末/闰年/停机跨月/时钟回拨；账本与额度一致且可解释。
4. **协议与网络**：生产批准的 sing-box 1.14.2 与目标 Mihomo 版本，逐支持协议/传输组合发真实请求；主 DNS 超时/SERVFAIL、备用失效、缓存恢复；住宅开启/关闭与普通自定义规则交叉验收。
5. **长连接**：持续 SSE/WebSocket/API 请求期间修改用户、重复发布、控制面升级，记录中断数、恢复时间和出口变化。尚未实现无损更新的路径应明示中断预期。
6. **终端实测**：iPhone Wi-Fi、蜂窝分别验证国内 App 图片/API、普通海外网站、AI 网页与 API；核对客户端命中规则/策略组/实际出口。涉及 TUN/系统代理时增加桌面应用、IPv6/NAT64 与切网验证。
7. **恢复与耐久**：干净主机恢复全部必需材料；24/72 小时观测句柄、RSS、事件循环、WAL/磁盘增长、任务与计量积压；真实业务恢复后才判定验收通过。
